# ADR-003 — 策略是术，系统是道，软件是容器

**日期**：2026-10-26  
**状态**：Accepted as a responsibility boundary; incremental implementation  
**范围**：Emergenzix 应用与 NEMT 理论仓库之间的架构责任划分

## 背景

一条策略的逻辑不能同时决定机会筛选、账户资金守恒、数据库结构和 UI。研究还发现：v5 有结算后按权益再定额，但它没有实现分批加仓；不能因为系统出现盈利，就允许策略随意修改风险预算或账户余额。

## 决策：恰好三个概念层

```text
[1] 交易策略：术 — Strategy
    观测数据 → 市场情境/信号 → 候选交易计划
    入场、趋势延续、分批触发、失效、退出假说
    各变体独立编号、风险前提和证据等级
                     ↓ 提出候选，不拥有资金
[2] 交易系统：道 — Trading System
    策略协调/许可 → 组合风险预算 → 权益账本 → 仿真/执行状态
    统一协调多策略冲突、真实现金流、组合敞口和持仓路径
    给出“可执行/应观望”结果与完整审计数据
                     ↓ 提供稳定接口
[3] 交易软件：容器 — Software/Delivery
    FastAPI、CLI、Telegram、Web、数据库、Docker、AWS
    接收用户输入“本金+时间周期”，持久化版本与证据
    不因部署媒介、API 或前端变化而修改策略和风险规则
```

- **策略仅能提出意图**：不能直接修改总账户权益、伪造已成交资金、越过组合预算、调用实盘下单。
- **系统拥有唯一真实会计口径**：市场/持仓状态、可用资金和策略之间的风险配额均由系统统一计算；系统不能把“最大收益”作为绕过风险控制的理由。
- **软件只承载和传递**：例如相同的 `initial_cash`、`period`、`start_date`，不论 API、CLI、Telegram 或 Web 发起，必须转换为同一版本化研究请求和可重现结果。

## NEMT 与 Emergenzix 的物理仓库边界

- `huliye24/Non-Equilibrium-Market-Theory`：理论假说、策略术、实验协议与证据；**纯研究 Markdown**，不放运行引擎。
- `huliye24/emergenzix`：系统道的**运行实现**和软件容器；策略实现可位于此仓库内，但需由理论仓库已审查、可追溯的版本驱动。

注意：“三层概念”不等于必须建立三家企业、三套服务器或拆成三个 GitHub 仓库。目前保持已有两个代码/研究仓库更实际。

## 本次实施范围：Equity Ledger A

新增的 `backend/emergenzix_api/equity_ledger.py` 仅是**已平仓权益账本基础模型**：

- 按净成交结果复利：100→120→132，亏损也按相同规则降低下一笔风险预算。
- 将费用和外部入金/提现独立记账；入金不能算交易收益。
- 以不可变、十进制快照和成交/划转 ID 拒绝重复入账，校验资产守恒。
- 避免暗示现有纯结算快照拥有浮盈、可用保证金、开放仓位、分批订单或清算建模能力；这些需要后续独立模块和集成验收。

该模块不连接 Telegram、API 下单、真实交易所、纸面订单、策略路由或已有不可变实验记录。它也不自动替换当前 v5 回测中的会计处理，因此**本次 CI 通过不等于历史策略按该账本重算完成**。

## 后续工程微任务

1. 在独立的版本化回测实验中对比原单仓权益结算与新账本，记录同一批成交的净收益及费用。
2. 引入多笔未平仓仓位的市值与保证金，建立可用资金/风险约束，无杠杆与衍生品必须分开。
3. 引入 S-003.1 的交易计划、分批订单和加仓；每批必须受**整个账户风险预算**约束。
4. 最后才将 S-003 的独立策略版本接入已有 `--capital` / `--period` 的快速回测入口。

**底线**：研究结论不代表交易许可；高收益目标不改变三层责任和风控边界。
